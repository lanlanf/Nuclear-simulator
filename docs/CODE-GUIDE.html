1. Architecture overview

There is one physics library and three programs that use it. The physics code never calls Arduino functions, so the code you test on your PC is byte-for-byte what runs on the board.

lib/reactor — physics library (C++11, float only)

params · kinetics · plant (rods + heat) · instruments · protection · reactor facade

desktop/sim_cli

Runs scripted scenarios on the PC and writes CSV. Built with CMake + g++.

tests/

doctest unit tests that check the physics against theory. Run with ctest.

src/ (firmware)

Uno R4: pots, buttons, LEDs, buzzer, servo, OLED and serial. Built with PlatformIO.

Python tools (tools/) solve the same equations with SciPy as an independent “answer key,” then compare it against the C++ and board CSV output and make the figures.

Data flow, every 10 ms:

  1. Inputs: rod demand, SCRAM, reset, optional reactivity override.
  2. Rod position and rod reactivity.
  3. Total reactivity: rod plus temperature feedback.
  4. Kinetics step to get power.
  5. Thermal step to get temperature.
  6. Period and SUR.
  7. Trip logic.
  8. Readings go out to the LEDs, servo, OLED and CSV.

2. Starting the project — important steps, in order

  1. Decide which computer. This is a work laptop, so check the policy or use a personal machine (see the earlier discussion). Everything below works on either.
  2. Install and verify the tools (§3). Don't write code until g++ --version, cmake --version, git --version and py --version all work in a fresh terminal.
  3. Clone the empty GitHub repo and set your personal identity for this repo only: 
    git clone https://github.com/lanlanf/Nuclear-simulator.git
cd Nuclear-simulator
git config user.name  "Landon Fancher"
git config user.email "36139453+lanlanf@users.noreply.github.com"
  4. Add the housekeeping files first: .gitignore, LICENSE (MIT), README.md (outline in §10), and copy PLAN.md/PLAN.html/this file into docs/. Commit with the message chore: project skeleton.
  5. Get an empty build passing. Create a CMakeLists.txt plus one dummy doctest test, and confirm ctest shows 1/1 passed. This proves the toolchain before any physics.
  6. Write down the units in params.h before writing any math: time in s, power normalized so 1 = 100%, reactivity as absolute Δk/k (dollars only for display), temperature in K.
  7. Fix the CSV format (t,rho,n,T,period,sur,rod,trip). The C++, the firmware and Python all use it.
  8. Write the first test before the solver: “critical reactor stays at power” (T1 in §8). Then write stepImplicit() until it passes.
  9. Order the parts early (BOM in PLAN.html §8) so shipping isn't on your critical path. The firmware phase needs them.
  10. Commit small and often with Conventional Commits: feat:, fix:, test:, docs:, build:, chore: [P17].
  11. Keep a dated engineering log (docs/LOG.md) recording what you tried, what failed and the plots. It feeds your report, README and scholarship essays.
  12. Blink the R4 with PlatformIO the day it arrives, before any reactor code goes on it. That isolates upload and driver problems.

5.1 Decisions & why

DecisionChoiceWhy (vs. alternatives)
Main solverFully coupled backward Euler (F7)
  • Stable at any step size: stiffness ratio ≈ (β/Λ)/λ₁ ≈ 65/0.0124 ≈ 5000 [F5].
  • Exact equilibrium: with F2 initial values, numerator = denominator algebraically, so a critical core can't drift except by float rounding.
  • Cheap: no matrix, about 60 flops.
  • Simple to explain in a report.
Comparison solversExplicit Euler (shows the blow-up); optional exponential-precursor variant \(C_i^{+}=C_ie^{-\lambda_ih}+\frac{\beta_in}{\lambda_i\Lambda}(1-e^{-\lambda_ih})\)These make good report figures. The piecewise-constant approximation (Kinard & Allen 2004 [F6]) is the literature reference method but needs a matrix exponential, which is too heavy to justify here. Cite it as related work.
Time step\(h=10\) ms on the board; sweep 1–20 ms on the PCAccurate enough for delayed-neutron time scales, and the R4 uses about 0.2% CPU. Use 10 substeps whenever \(\rho\ge\beta\) (see §5.2).
Data setKeepin 6-group, \(\beta=0.0065\), \(\Lambda=10^{-4}\) sThe textbook standard, so it matches Lamarsh and the class. Comment in code that this is the physical β, not \(\beta_\text{eff}\).
Thermal modelOne lumped node (F16), demo-scaled constantsShows self-stabilization with 3 parameters. A two-node fuel/coolant model (Bickel [F12] slide 16) is a stretch goal.
Period meterWindowed log-power slope over 1 s (F18), smoothedA per-step ratio \(n_k/n_{k-1}\) is about \(1+10^{-4}\), close to float precision (\(\varepsilon\approx1.2\times10^{-7}\) [P11]), so it is noisy.
Validation referenceSciPy solve_ivp(method="Radau", rtol=1e-8, atol=1e-12) and the 6-group inhour root from brentqSciPy's docs recommend Radau/BDF for stiff systems [I15]. Use the exact inhour root, because the approximations are 20–50% off (next section).
Source strength\(S\approx3\times10^{-4}\ \text{s}^{-1}\)From F13: at \(\rho=-\$5\), shutdown power is about \(10^{-6}\), which gives about 6 decades of log-power startup to watch.
ShutdownTwo rod banks: a regulating rod (pot, worth \$9) and a safety bank (worth about \$4, driven by SCRAM/reset)DOE separates shim, regulating and safety rods [F11]. The regulating rod alone gives −\$4.5 hot but only about −\$1.05 cold, because cooling adds +\$3.46. Both banks in give −\$8.5 ≈ −5.5% hot.

5.2 Math gotchas the code must handle

Approximations vs. the exact inhour equation:
StepExact 6-group inhourOne group, λ = 0.1 (DOE, power rising)One group, λ = 0.08Small-ρ formula
+100 pcm55–57 s (Lamarsh: 57 s [F7])55 s69 s85 s
+\$0.1≈ 98 s90 s113 s130 s
+\$0.5≈ 5.8 s10 s12.5 s26 s
DOE explains the gap: while power rises, short-lived precursors dominate, so \(\lambda_\text{eff}\) is not a constant [F11]. One group gets worse as ρ grows. Test against the exact root, not the approximations.
Implicit denominator above prompt critical. The F7 denominator is \(1-\frac{h(\rho-\beta)}{\Lambda}-\dots\). With \(h/\Lambda=100\), it becomes ≤ 0 once \(\rho-\beta\gtrsim0.01\) (about \$2.5).
  • Rule 1: if \(\rho\ge\beta\), use 10 substeps.
  • Rule 2: assert that the denominator is > 0.
  • Rule 3: trip immediately.
The rod design (max about +\$1.1) keeps you below the limit anyway.
Float overflow and NaN. Clamp \(n\le10^{6}\). Check isfinite() on \(n\) and \(T\) every step, and treat non-finite values as a fault trip [P12].
Thermal coupling is explicit. Feedback uses the temperature from the previous step. That's fine because the thermal time constant (7.5 s) is much slower than 10 ms.

6. Physics library — what goes in each file

params.h

  • A units comment block.
  • struct KineticsParams { int groups; float beta[6]; float lambda[6]; float Lambda; }.
  • A keepinU235() function that returns the defaults. A one-group version is also handy for tests.
  • struct PlantParams: rod worth \(\rho_w\), \(\rho_\text{crit}\), safety-bank worth \(\rho_s\approx\$4\), rod speed, scram speed, \(MC\), \(K\), \(T_c\), \(\alpha_T\), \(S\).
  • struct Setpoints: power trip 1.20, temperature trip, period trip 10 s, warning levels.
// Units: s, normalized power (1 = 100 %), reactivity in dk/k, K.
// beta here is physical U-235 beta, not beta_eff.
inline KineticsParams keepinU235() {
  KineticsParams p = {6,
    {0.000215f,0.001424f,0.001274f,0.002568f,0.000748f,0.000273f},
    {0.0124f,0.0305f,0.111f,0.301f,1.14f,3.01f},
    1.0e-4f};
  return p;
}

kinetics.h / kinetics.cpp

  • struct Kinetics { float n; float C[6]; };
  • void initEquilibrium(Kinetics&, const KineticsParams&, float n0); (F2)
  • void stepImplicit(Kinetics&, const KineticsParams&, float rho, float S, float h); (F7). Uses substeps when \(\rho\ge\beta\), asserts the denominator is > 0, and clamps \(n\).
  • void stepExplicit(...) (F8), used only for the instability demo and tests.
  • float totalBeta(const KineticsParams&).

plant.h / plant.cpp

  • float rodWorth(float x, const PlantParams&) (F14), using sinf.
  • float moveRod(float x, float demand, float speed, float h) (F15). The SCRAM path calls it with the fast scram speed (about 1 s full stroke) and demand 0.
  • The safety bank is a second position \(s\in[0,1]\) that uses the same moveRod and S-curve. A successful reset withdraws it at normal speed; a trip drives it in at scram speed.
  • float stepTemperature(float T, float P, const PlantParams&, float h) (F16).
  • float feedback(float T, const PlantParams&) (F17).
float stepTemperature(float T, float P, const PlantParams& p, float h) {
  return (T + (h / p.MC) * (P + p.K * p.Tcool)) / (1.0f + h * p.K / p.MC);
}

instruments.h / instruments.cpp

  • struct PeriodMeter holding a ring buffer of 11 samples of logf(n), taken every 0.1 s (a 1 s window), plus an EMA-smoothed period.
  • void update(PeriodMeter&, float n, float h). The period is reported as “∞” (a large sentinel) when \(|\Delta\ln n|\) is tiny.
  • float sur(float period) (F19); float logPower(float n) (F20).

protection.h / protection.cpp

  • Trip bit flags: TRIP_MANUAL=1, TRIP_HIGH_POWER=2, TRIP_HIGH_TEMP=4, TRIP_SHORT_PERIOD=8, TRIP_PROMPT_CRIT=16, TRIP_FAULT=32.
  • uint8_t evaluate(readings, setpoints) returns the new trip bits. These are OR-ed into a latched word.
  • bool tryReset(latched, rodPos) only clears the latch if the rods are fully in (\(x<0.01\)) and no trip condition is still present.
  • A warning level (not a trip) for the yellow LED and buzzer beeps: \(P>1.05\), \(\tau<30\) s, or high temperature.
  • Rod stop: while any warning is up, Reactor::step blocks rod withdrawal (insertion always works). This keeps an off-centre pot at power-on and a one-turn cold startup from tripping.

reactor.h / reactor.cpp — the only thing firmware and CLI call

struct Inputs   { float rodDemand; bool scram; bool reset; bool overrideOn; float rhoOverride; };
struct Readings { float t, n, rho, rhoDollars, T, period, sur, logP, rod; uint8_t trips, warn; };

class Reactor {
public:
  void init();                                // equilibrium at n0, T = Tref, rods at critical position
  const Readings& step(const Inputs& in, float h);
};

Order inside step():

  1. Move the regulating rod and the safety bank (both in at scram speed if latched).
  2. Compute ρ = regulating rod + safety bank + feedback, or the override value.
  3. stepImplicit.
  4. stepTemperature.
  5. Update the period meter.
  6. Run evaluate and latch.
  7. Fill in Readings.

7. Firmware (src/) — what goes in each file

main.cpp: fixed-step loop with accumulator

The loop runs the physics in fixed 10 ms steps. Elapsed time builds up in an accumulator, and the number of catch-up steps per loop is capped so a slow OLED draw (about 25 ms) can't cause a “spiral of death” [P1][P2].

const uint32_t DT_MS = 10; const float DT_S = 0.010f; const uint8_t MAX_STEPS = 10;
uint32_t lastMs, accMs;

void loop() {
  uint32_t now = millis();
  accMs += now - lastMs; lastMs = now;            // unsigned subtraction survives millis() wrap
  if (accMs > 250) accMs = 250;
  uint8_t steps = 0;
  while (accMs >= DT_MS && steps < MAX_STEPS) {
    const Readings& r = reactor.step(panel.readInputs(), DT_S);
    panel.show(r);                                // LEDs, buzzer, servo
    accMs -= DT_MS; ++steps;
  }
  handleSerialCommands();
  every100ms(printReadings);                      // plotter / CSV / Teleplot
  every200ms(display.draw);                       // OLED at 5 Hz
}

panel_io.h / panel_io.cpp

  • Pots: analogRead(A0) at 14 bits (÷ 16383), then an EMA filter \(y\leftarrow y+0.1(x-y)\). Rod demand 0–1; coolant 285–295 K.
  • SCRAM button (D2): interrupt on FALLING. The ISR only sets a volatile flag [P3]. It needs no debounce because the trip latches anyway.
  • Reset/acknowledge button (D3): needs a 30 ms debounce in loop().
  • LEDs:
    • Green: operating normally.
    • Blue: critical, \(|\rho|<\) 5 pcm and \(|\tau|\) large.
    • Yellow: warning.
    • Red: tripped.
  • Buzzer: on continuously while a trip is unacknowledged; short beeps on a warning.
  • Servo: servo.write(180*x) with a 600–2400 µs pulse range (so an SG90 doesn't stall on its end stop), updated only when the angle changes by ≥ 1°.

FileDoes
reference.pySame 7 ODEs, plus the thermal and feedback model, solved with solve_ivp(method="Radau", rtol=1e-8, atol=1e-12). Writes CSV with the same columns. Has an inhour_root(rho) helper using scipy.optimize.brentq.

requirements.txtnumpy, scipy, matplotlib, pyserial
def rhs(t, y, rho_of_t, p):
    n, C = y[0], y[1:]
    rho = rho_of_t(t)
    dn = (rho - p.beta) / p.Lam * n + np.dot(p.lam, C) + p.S
    dC = p.beta_i / p.Lam * n - p.lam * C
    return np.concatenate(([dn], dC))

def inhour_root(rho, p):          # positive stable period for 0 < rho < beta
    f = lambda T: p.Lam / T + np.sum(p.beta_i / (1 + p.lam * T)) - rho
    return brentq(f, 1e-6, 1e7)

11. Coding rules (so it runs the same on PC and board)

RuleWhy
float only; write literals with f (0.5f); use sinf/expf/logfThe Cortex-M4 FPU handles single precision; double is emulated in software. -Wdouble-promotion catches slips [P4].
No STL, new, exceptions or iostream in lib/reactorKeeps it Arduino-portable, with no heap fragmentation
No millis()/delay() in the physics; pass h inThat is what makes the code testable on the PC
No delay() anywhere in the firmwareIt would stall the physics clock [P2]
ISR variables are volatile; keep ISRs to one lineArduino reference [P3]
Never compare floats with ==; use doctest::Approx\(\varepsilon_\text{float}\approx1.19\times10^{-7}\) [P11]
isfinite() guard on the state every stepNaN should trip the reactor rather than spread silently [P12]
One header comment per file giving its job, and units on every parameterReaders (and future you) need units to check the math
Build with zero warningsThe warning flags catch real float bugs

Stretch goals (only after M7). DOE Vol. 2 [F11] and Bickel [F12] supply the data:
  • Two-node feedback: a fuel node with \(\tau_f\approx\) 3–5 s and a Doppler coefficient, plus a slower coolant node with the moderator coefficient [F12].
  • Decay heat: about 5–6% of power right after shutdown, under 1% after one hour.
  • Xenon-135: I-135 half-life 6.57 h, Xe-135 half-life 9.10 h, \(\sigma_a=2.6\times10^6\) b. Xenon peaks about 10–12 h after shutdown (DOE about 10 h, Bickel about 11.6 h). This needs a time-acceleration mode.
